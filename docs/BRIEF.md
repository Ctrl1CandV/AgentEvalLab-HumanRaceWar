## 3. 工作规则

### 3.1 安全

- 不读取、不打印、不保存任何凭据、令牌和密钥，也不把它们写进代码、日志、回放或提交。
- 所有 bot 代码只在沙箱里运行（DESIGN 6.1），对局不联网。
- 不关闭、不绕过用户机器上的代理和安全设置。
- 构建时可以联网查文档和资料，确保开发质量。对局和 bot 运行不联网。框架仍只用标准库，安装新工具仍先问用户。被测模型全程离线，只能用工作区提供的内容写 bot、测试和评价（D10）。

### 3.2 公开与保密（DESIGN 第 16 节）

- 这个仓库是公开的。隐藏内容只能放在 `private/`。
- 每次克隆后，运行一次 `git config core.hooksPath .githooks`。不要用 `--no-verify` 跳过检查。
- 每个隐藏文件（隐藏 bot、隐藏地图）的 sha256 写进 `private/HIDDEN.sha256`，格式和 `sha256sum` 的输出相同。pre-commit 检查会用它，拦住"把隐藏文件复制到公开目录"这类错误。
- 公开的报告和数据里，隐藏 bot 只写代号、风格、sha256 和统计数据，不写实现，也不写弱点。
- 用户2026-11-08补充：远端只放审查内容与汇总；实际对局回放、逐局表和索引均留本机，公开bot示例也不上传。
- 如果发现隐藏内容被推送了，停下来，告诉用户（DESIGN 第 16 节）。

### 3.3 改动的权限

| 你可以直接做 | 可以做，但要写进 rules/CHANGELOG.md 和 STATUS.md | 要先等评测负责人同意 |
|---|---|---|
| 实现细节、代码结构、工具、测试、性能优化 | 附录 A 范围内的参数调整，附上依据的数据 | 改规则机制、结算顺序、胜负条件、协议格式；改计分方式、阶梯的构成原则、任何验收指标 |

- 规则文档和引擎必须一致：改了一处，就改另一处，并补上例子测试。
- 遇到设计没写清楚的地方：
  - 先按最简单、对两方对称、不引入隐藏机制的方式做；
  - 在 STATUS.md 的"需要决定的事"里写明你的做法，等确认。

### 3.4 评分原则

- 难度不能来自隐藏要求、格式陷阱或框架限制。游戏规则和提交格式全部公开，但计分细节不告诉被测模型；模型目标是尽力赢（D8）。
- 不为了让某个指标好看而改数据、挑数据。所有对局的结果都留在结果库里，报告用全部数据。
- 指标没达到，就如实写没达到，并分析原因。

### 3.5 提交和同步

- 小步提交，每次提交写明做了什么。今后署名 `gpt-6-astra`，使用 GitHub noreply 邮箱，不改写历史；若影响正常提交或推送，保持现状并在 STATUS 说明（S7）。
- 构建进行中的日子，每天至少更新一次 STATUS.md。
- 阶段结束时：
  1. 写 `reports/phase-X.md`；
  2. 更新 `data/` 和 `logs/`；
  3. 重新生成 MANIFEST.sha256；
  4. 停下来。
- 大文件不进仓库：
  - `runs/`（全部对局和回放）在 .gitignore 里；
  - `replays/` 只保留说明；不上传实际回放，覆盖此前“最多10局小型公开示例”的许可。
  - `data/` 只放聚合矩阵、统计与审查汇总；原始逐局数据和旧完整日志集中在本机归档，不能因整理目录而丢弃失败证据。

### 3.6 环境

- 系统：Linux 或 WSL2（Ubuntu 22.04 或更新）。
- 软件：Python 3.13、GCC 11、bubblewrap 0.6 或更新，和评测机器的大版本一致（DESIGN 3.4）。
- 框架只用 Python 标准库。
- 所有性能数据都注明你的机器配置（CPU 型号、核数、内存）和速度系数。

### 3.7 额度和算力

- 大批对局（校准、调参、自我对弈）只用CPU，不调用模型。
- 用户2026-11-08决定不再记录构建阶段token用量；既有历史快照保留，不再采集会话用量。
- CPU小时照旧记录，区分bot、宿主、编译和校验等范围，避免重复相加；无法完整计量的部分明确标未知。
- 此决定不取消第5.3节标准预算自测的正式预算、隔离要求与该测试自身的预算记录。

## 4. A 阶段：游戏和框架

### 4.1 建议的顺序

先打通一局，再做完整，最后调平衡。已有引擎和首局闭环不重做；2026-11-07 中途审查后的优先顺序覆盖下面的初始计划：

1. 落实已批准设计与用户决定，先修 M1、M2、M3、M5、M6，并用真实 bwrap 补回归测试。
2. 实现 `bench --jobs N` 和速度折算，记录本机负载曲线及逐核差异（M4/Q2）。
3. 按步行距离修地图生成/检查，升生成器版本并重新生成地图（M7）。
4. `check`、调度器、结果库、`tournament`，包含内容摘要编译缓存和全局 CPU 分配（S3/S4）。结果库记录原始指标，不冻结过程分公式。
5. 动物园；按新口径跑矩阵、bootstrap、平衡和效率检查（M8/Q3），最后整理 A 阶段报告和 MANIFEST，再停止等审查。

**本次已批准设计条目（具体要求以 DESIGN 对应节为准）：**

| 条目 | 纳入的要求 |
|---|---|
| D1 | 不挂载宿主 `/etc`，加 `--cap-drop ALL`；C++ 命令加 `-I/sdk`。 |
| D2 | 强制单进程、有限线程、禁止改变绑核；`/tmp` 总量≤64 MiB，若只读须公开；编译地址空间 2 GiB，运行时 512 MiB。 |
| D3 | CPU 按相邻 READY/END 累计读数之差扣费，END 后工作计入下一回合。 |
| D4 | 参考为评测机空闲单实例，现测与实际并行度一致；2N 个绑定 CPU 同时测，取中位数；所有时限、储备、墙钟和硬上限一起折算，并行度保持不变。 |
| D5 | 每格家门矿步行距离≤12；至少一半塔基与矿曼哈顿距离3–5且相邻空地间步行≤6；不合格换种子，不放宽标准。 |

### 5.1 做法

- **主线 bot：** 先为三种风格（进攻、经济、控制）各做一个强 bot 的主线版本。
- **强度档：** 用限制算力或去掉部分功能的办法做出强度档，填进各级（DESIGN 11.1）。
- **顶端：** 用多轮会话长时间开发，再用大批自我对弈调参。调参用 CPU 跑，不调用模型。
- **同样的限制：** 阶梯 bot 和被测模型的提交受同样的时限和资源限制。
- **记录：** 每个阶梯 bot 记下代号、风格、作者模型、开发方式（会话数、调参用的对局数）和 sha256，写进 `private/ladder-notes.md`。公开的 `ladder/ladder.json` 只写代号、风格、sha256 和 Elo。

- `ladder-ratings.csv`：Elo 和区间。

### 5.3 两项测试的要求

- 两个新会话，预算相同。
- 能看到阶梯代码的那个会话，不能复制阶梯 bot 的代码，只能利用对它们行为的了解。

**标准预算自测（11.5 第 6 条）：**

## 7. 报告格式（reports/phase-X.md）

1. **做了什么：** 对照交付清单逐项写。
2. **验收指标：** 每一条的结果、对应的数据文件、是否达到。
3. **规则和参数的改动：** 引用 CHANGELOG 的条目。
4. **问题和风险：** 发现了什么，哪些还没解决。
5. **需要决定的事：** 需要评测负责人或用户决定的事。
6. **用量：** CPU小时及计量边界、机器配置；不再统计构建token。标准预算自测另按第5.3节记录其正式预算执行情况。

- 不在公开仓库里放隐藏内容。
- 不跳过停点。
- 不给框架引入 Python 第三方包。
- 不为了通过验收而放宽测试、删掉对局数据，或者只报好的结果。
