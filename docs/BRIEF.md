## 3. 工作规则

### 3.1 安全

- 不读取、不打印、不保存任何凭据、令牌和密钥，也不把它们写进代码、日志、回放或提交。
- 所有 bot 代码只在沙箱里运行（DESIGN 6.1），对局不联网。
- 不关闭、不绕过用户机器上的代理和安全设置。
- 对局、bot 和构建过程都不从网上下载代码或数据。开发工具需要安装时，先问用户。

### 3.2 公开与保密（DESIGN 第 16 节）

- 这个仓库是公开的。隐藏内容只能放在 `private/`。
- 每次克隆后，运行一次 `git config core.hooksPath .githooks`。不要用 `--no-verify` 跳过检查。
- 每个隐藏文件（隐藏 bot、隐藏地图）的 sha256 写进 `private/HIDDEN.sha256`，格式和 `sha256sum` 的输出相同。pre-commit 检查会用它，拦住"把隐藏文件复制到公开目录"这类错误。
- 公开的报告和数据里，隐藏 bot 只写代号、风格、sha256 和统计数据，不写实现，也不写弱点。
- 公开的回放只放公开 bot 之间的对局。
- 如果发现隐藏内容被推送了，停下来，告诉用户（DESIGN 第 16 节）。

### 3.3 改动的权限

| 你可以直接做 | 可以做，但要写进 rules/CHANGELOG.md 和 STATUS.md | 要先等评测负责人同意 |
|---|---|---|
| 实现细节、代码结构、工具、测试、性能优化 | 附录 A 范围内的参数调整，附上依据的数据 | 改规则机制、结算顺序、胜负条件、协议格式；改计分方式、阶梯的构成原则、任何验收指标 |

- 规则文档和引擎必须一致：改了一处，就改另一处，并补上例子测试。
- 遇到设计没写清楚的地方：
  - 先按最简单、对两方对称、不引入隐藏机制的方式做；
  - 在 STATUS.md 的"需要决定的事"里写明你的做法，等确认。

### 3.4 评分原则

- 难度不能来自隐藏要求、格式陷阱或框架限制。
- 不为了让某个指标好看而改数据、挑数据。所有对局的结果都留在结果库里，报告用全部数据。
- 指标没达到，就如实写没达到，并分析原因。

### 3.5 提交和同步

- 小步提交，每次提交写明做了什么。
- 构建进行中的日子，每天至少更新一次 STATUS.md。
- 阶段结束时：
  1. 写 `reports/phase-X.md`；
  2. 更新 `data/` 和 `logs/`；
  3. 重新生成 MANIFEST.sha256；
  4. 停下来。
- 大文件不进仓库：
  - `runs/`（全部对局和回放）在 .gitignore 里；
  - `replays/` 每次更新最多 10 局、每局不超过 200 KB，只放公开 bot 之间的对局。

### 3.6 环境

- 系统：Linux 或 WSL2（Ubuntu 22.04 或更新）。
- 软件：Python 3.13、GCC 11、bubblewrap 0.6 或更新，和评测机器的大版本一致（DESIGN 3.4）。
- 框架只用 Python 标准库。
- 所有性能数据都注明你的机器配置（CPU 型号、核数、内存）和速度系数。

### 3.7 额度和算力

- 你用的是用户的 GPT 订阅额度。
- 大批对局（校准、调参、自我对弈）只用 CPU，不调用模型。
- 粗略估计：
  - A 阶段 10–30M token；
  - B 阶段 30–80M token，阶梯顶端的长时间开发和两项自测占大头；
  - C 阶段 5–15M token。

  如果某个阶段可能超出估计的一半以上，先在 STATUS.md 里说明，等用户决定。
- 在 STATUS.md 里记录每个阶段实际用的 token 和 CPU 小时。

## 4. A 阶段：游戏和框架

### 4.1 建议的顺序

先打通一局，再做完整，最后调平衡。

1. 引擎：状态、指令解析、结算（DESIGN 第 4 节）。每条规则至少一个例子测试。
2. 运行器（先用 plain 启动器）、协议（第 5 节）、SDK 和示例 bot、match 和 replay 工具。到这一步，先打通一局。
3. 地图生成器（第 7 节），生成 public 和 scrimmage 地图集。
4. bwrap 启动器、按 CPU 时钟计时、速度基准、出错的处理（第 6 节）。
5. 调度器、结果库、tournament 工具。
6. 动物园的 bot（10.1），全部用 SDK 写。
7. 平衡：跑动物园矩阵，按 10.3 调参。
8. 效率测量（6.4）、确定性和对称测试、健壮性测试（10.2 第 8–10 条）。
9. 写给被测模型的规则文档 `rules/rules.md`（9.3）。
10. 写阶段报告。

### 4.2 交付和验收

- 交付和验收标准见 DESIGN 第 17 节 A 阶段。
- data/ 里至少要有：
  - `zoo-matrix.csv`：每对 bot 的局数、胜、平、负，分地图类型；
  - `balance.json`：先后手、平局率、对局长度分布、结束方式；
  - `timing.json`：引擎、运行器、整局的用时，注明机器配置。
- logs/ 里至少要有：`determinism.log`、`robustness.log`、`issues.md`。
- `rules/CHANGELOG.md` 记录每一次参数调整。

### 4.3 停点

A 阶段结束后：
1. 在 STATUS.md 写"A 阶段完成，等待审查"；
2. 停下来，等 `inbox/` 里的审查意见。

评测负责人会重点审查规则有没有漏洞、平衡数据是否可信。

## 5. B 阶段：对手阶梯

### 5.1 做法

- **主线 bot：** 先为三种风格（进攻、经济、控制）各做一个强 bot 的主线版本。
- **强度档：** 用限制算力或去掉部分功能的办法做出强度档，填进各级（DESIGN 11.1）。
- **顶端：** 用多轮会话长时间开发，再用大批自我对弈调参。调参用 CPU 跑，不调用模型。
- **同样的限制：** 阶梯 bot 和被测模型的提交受同样的时限和资源限制。
- **记录：** 每个阶梯 bot 记下代号、风格、作者模型、开发方式（会话数、调参用的对局数）和 sha256，写进 `private/ladder-notes.md`。公开的 `ladder/ladder.json` 只写代号、风格、sha256 和 Elo。

### 5.2 校准和验收

按 DESIGN 11.4 和 11.5。data/ 里要有：
- `ladder-matrix.csv`：只写代号；
- `ladder-ratings.csv`：Elo 和区间。

### 5.3 两项测试的要求

**可钻空子测试（11.5 第 5 条）：**
- 两个新会话，预算相同。
- 能看到阶梯代码的那个会话，不能复制阶梯 bot 的代码，只能利用对它们行为的了解。

**标准预算自测（11.5 第 6 条）：**
- 在一个干净的目录里做。目录里只有给被测模型的公开材料，从 package/ 的清单复制过来。
- 不能有这个仓库、`private/`、你的笔记，也不能有任何跨会话的记忆。如果你的工具有记忆功能或 AGENTS.md 一类的文件，要关掉，或者在干净的目录里运行。
- 严格按流程：
  1. 第一阶段：6M token、2.5 小时；
  2. 练习赛；
  3. 第二阶段：新会话，8M token、3 小时。
- 结果写进 `data/standard-budget.json`：投入的 token 和时间、主分数、每一级的成绩。

### 5.4 停点

B 阶段结束后停下来，等审查。

## 7. 报告格式（reports/phase-X.md）

1. **做了什么：** 对照交付清单逐项写。
2. **验收指标：** 每一条的结果、对应的数据文件、是否达到。
3. **规则和参数的改动：** 引用 CHANGELOG 的条目。
4. **问题和风险：** 发现了什么，哪些还没解决。
5. **需要决定的事：** 需要评测负责人或用户决定的事。
6. **用量：** 模型 token、CPU 小时、机器配置。

## 8. 不要做的事

- 不改设计里的计分方式和验收指标。要改，先提出来。
- 不在公开仓库里放隐藏内容。
- 不跳过停点。
- 不给框架引入 Python 第三方包。
- 不为了通过验收而放宽测试、删掉对局数据，或者只报好的结果。
