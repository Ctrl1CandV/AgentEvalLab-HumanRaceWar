## 0. 一页概要

- **被测模型做什么：** 读规则，写一个 bot 程序（Python 或 C++），用公开对手和本地工具测试。分两个阶段：先做出能用的版本；框架让它和公开 bot 打一场练习赛，再根据结果优化。
- **第一款游戏"前哨"：**
  - 两人同时行动的格子即时战略游戏。
  - 每方一个基地，造工兵和战士，采矿，在塔基上建塔占地盘，打仗。
  - 摧毁对方基地立即获胜；否则 300 回合后比塔的累计得分。
- **分数：**
  - 只看对一条固定对手阶梯的战绩。阶梯约 12 级，每级有 2–3 个强度相近、风格不同的 bot。
  - 每局得分以胜负为主，过程分权重较低；75%/25% 仅为当前雏形，具体指标和权重待实际测试与大规模运行后确定。
  - 主分数 = 各级得分的平均，在 0 到 1 之间。
  - 同场的其他模型是谁，不影响分数。
- **扩展：**
  - 阶梯可以一直往上加级，这是"量"。
  - 游戏可以加变体，也可以再加新游戏，这是"质"。
  - 引擎是确定性的，对局全部存档，旧的提交可以在新版本上重新评分。
- **构建：** 分 A、B、C 三个阶段，每个阶段结束都停下来，等审查。

## 1. 目标与原则

### 1.1 目标

1. **有竞技性，有周旋余地。** 几条取胜路线互相克制，最强的打法要看局面调整；没有一种死板打法能一路通吃。
2. **分数不取决于同场的对手。** 只看对固定阶梯的成绩。用户的要求：让弱模型写和让最强的模型写，对手强弱完全不同，所以不能用模型之间互相打的成绩计分。
3. **能拉开顶尖模型：**
   - astra 在标准预算下的主分数不超过 0.7，最好不超过 0.6；
   - 弱模型只要写出能用的 bot，就能拿到约 5% 以上。
4. **能扩展。** 阶梯往上加级；游戏加变体、加新游戏。回放格式为以后的可视化留好接口。
5. **安全、稳定、高效、可以复现。**

### 1.2 评分原则（AgentEvalLab 的原则，必须遵守）

- **难度不能来自隐藏要求、格式陷阱或框架限制。**
  - bot 需要知道的游戏规则和运行要求全部公开，没有隐藏机制。计分细节不告诉被测模型；模型的目标就是尽力赢，所以这不算隐藏要求（D8）。
  - 协议是容错的：格式上的小错只记警告，不判负。
- **版本不可变。** 发布后的规则、地图、阶梯、评分器都不再改；要改就发新版本。
- **先找根本原因，再改。**
- **计分规则（第 12 节）的改动要经用户同意。**

### 1.3 第一版的范围：先做出可用、可行的版本

v1 只包括：
- 一款游戏（前哨）；
- 两人对局，完全信息，没有战争迷雾；
- 两种单位、两种建筑；
- 用 ASCII 文字查看回放。

可视化、迷雾、第三种单位、科技、四人混战都放到以后（第 15 节），但 v1 的架构要给它们留好位置。

## 2. 先例与借鉴（摘要）

完整的调研见 AgentEvalLab 的 `docs/design/PLAN-008-DESIGN.md` 第 7.1 节。对本设计影响最大的几点：

| 先例 | 借鉴 |
|---|---|
| CodeClash、CC:Ladder | 让模型写 bot 对战，能有效区分模型。用固定的人类 bot 阶梯，可以消除"对手是谁"带来的波动；模型都停在阶梯底部，说明余量很大 |
| RobotRumble | 多单位格子战。人类 bot 之间相差约 5000 Elo，强弱差距很大 |
| Halite、Lux AI（Kaggle） | 采矿、运输、卸货点、扩张这类经济机制，策略空间很深 |
| CodinGame 联赛 | 每级一个"守门 bot"。协议用简单的文本行，C++ 和 Python 都好写 |
| Gauntlet | 冻结提交，在留出的地图上评测。本地测试通过，不代表在留出地图上也行 |
| Nash averaging、Spinning Tops | 互相克制的循环会让 Elo 失真，重复的同类对手会扭曲平均分。所以每级放几个风格不同的 bot，级内平均 |
| Stockfish 的 fishtest | 同一张图交换先后手成对对局；按机器速度折算时限；用序贯检验节省局数 |

## 3. 总体架构

### 3.1 框架和游戏分开

```
arena/core/            和具体游戏无关的部分：
                       对局运行器、沙箱启动器、计时、并行调度、结果库、
                       评级（Bradley–Terry Elo、bootstrap 区间）、阶梯、评分器、联赛、命令行
arena/games/outpost/   前哨：规则参数、状态、观察消息与指令解析、结算、地图生成、ASCII 渲染
```

游戏模块实现一组固定的接口（3.3），框架只通过这组接口调用游戏。以后加第二款游戏，只需要写一个新的 `arena/games/<名字>/`，框架、阶梯、评分器全部复用。

### 3.2 目录结构

```
README.md、STATUS.md、MANIFEST.sha256
docs/              DESIGN.md（本文件）、BRIEF.md（任务书）
rules/             rules.md（给被测模型的规则全文）、CHANGELOG.md（规则和参数的改动记录）
arena/             框架和游戏（Python 包，只用标准库）
sdk/python/、sdk/cpp/   bot 的输入输出库和示例 bot
bots/public/       公开的 bot：策略动物园、阶梯 L0–L2
maps/public/、maps/scrimmage/   公开地图集
ladder/            ladder.json（各级、各 bot 的代号、风格、sha256、Elo；不含隐藏 bot 的代码）
package/           给被测模型的公开材料清单，两个阶段的说明草稿
tests/             单元测试、规则例子测试、确定性和对称性测试、健壮性测试
reports/、data/、logs/、replays/、inbox/   同步和审查用（见各目录的 README.md）
.githooks/         pre-commit 检查（第 16 节）
private/           隐藏内容，不入库（.gitignore）
runs/              全部对局结果和回放，不入库（.gitignore）
```

### 3.3 游戏接口

```python
class Game:
    id: str                                                      # "outpost"
    def new_match(self, map_text: str, ruleset: dict, seeds: list[int]) -> State
    def init_message(self, state, player: int) -> list[str]     # 开局消息（第 5.2 节）
    def observation(self, state, player: int) -> list[str]      # 每回合的消息（第 5.3 节）
    def parse_orders(self, state, player: int, lines: list[str]) -> tuple[Orders, list[Warning]]
    def step(self, state, orders: list[Orders]) -> list[Event]  # 结算一回合（第 4.4 节）
    def result(self, state) -> Result | None                    # 对局结束时返回结果
    def state_hash(self, state) -> str                          # 规范序列化后 SHA-256 的前 16 个十六进制字符
    def render(self, state) -> str                              # ASCII 棋盘
```

对接口的要求：
- **确定性。** `step` 只用整数运算，不读时间，不用随机数。随机只出现在地图生成里，而且用自带的伪随机数生成器（7.1）。
- **对称。** 把两方的编号对调、地图旋转 180°，结算的结果和事件也完全对称（10.2 第 9 条测试这一点）。
- **玩家数。** 接口按"若干个玩家"写，不把两个玩家写死，给以后的四人混战留位置。

## 4. 游戏 v1"前哨"的规则

### 4.1 地图

- **大小和坐标：** 方格地图，宽 W、高 H，都在 24 到 40 之间。坐标是 (x, y)，原点在左上角，x 向右（东）增大，y 向下（南）增大。
- **格子：**

  | 符号 | 格子 | 能否进入 |
  |---|---|---|
  | `.` | 空地 | 可以，单位只能站在空地上 |
  | `#` | 墙 | 不能 |
  | `O` | 矿，有储量 | 不能 |
  | `S` | 塔基 | 不能 |
  | `0`、`1` | 0 号、1 号玩家的基地 | 不能 |

  塔建好以后，也不能进入。
- **对称：** 地图关于中心点 180° 旋转对称，(x, y) 和 (W−1−x, H−1−y) 互为对称点；两个基地也互为对称点。
- **距离：** 游戏动作使用曼哈顿距离 |dx| + |dy|。"相邻"指距离为 1，也就是上下左右四格。地图生成另按 7.2 检查可步行路径，不能用曼哈顿距离代替（D5）。
- **矿：** 采完后储量为 0，仍然是不能进入的矿格。

### 4.2 实体和数值

下表是 ruleset `standard-1` 的起点，可调的范围见附录 A。

| 实体 | 造价 | 生命 | 伤害 | 其他 |
|---|---:|---:|---|---|
| 工兵 W | 40 | 60 | 10，打相邻的目标 | 每回合采矿 10，最多携带 60；能建塔 |
| 战士 S | 80 | 100 | 20，打相邻的目标 | — |
| 基地 | — | 600 | 射击 10，射程 2 | 见下 |
| 塔 | 150 | 300 | — | 见下 |

- **基地：**
  - 每回合最多生产 1 个单位，放在距离基地 2 以内的空地上；
  - 距离基地 2 以内的己方单位，每回合回复 5 生命。
- **塔：**
  - 建在空塔基上；
  - 占有方每回合得 1 分；
  - 塔也是卸货点。
- **开局：** 每方基地满血，能量 500，有 4 个工兵，位置在基地附近，两方对称。
- **人口上限：** 40，工兵和战士合计。
- **回合上限：** 300。

### 4.3 指令

- 每回合每个单位最多一条指令；基地最多一条生产指令、一条射击指令。
- 没有指令的单位原地不动。
- 下表的条件都按回合开始时的局面判断。

| 指令 | 谁发 | 条件 | 效果 |
|---|---|---|---|
| `MOVE id 方向` | 工兵、战士 | 方向是 N、E、S、W 之一 | 移动一格，冲突时按 4.4 的规则 |
| `ATTACK id x y` | 工兵、战士 | (x, y) 上是敌方的单位、塔或基地，而且和这个单位相邻 | 造成这个单位的伤害 |
| `MINE id x y` | 工兵 | (x, y) 是储量大于 0 的矿，和工兵相邻，工兵的携带量没满 | 采矿 |
| `BUILD id x y` | 工兵 | (x, y) 是空塔基，和工兵相邻 | 花 150 能量建塔 |
| `SPAWN 类型 x y` | 基地 | 类型是 W 或 S；(x, y) 是空地，距己方基地不超过 2；能量够；人口没到上限 | 生产一个工兵或战士 |
| `FIRE x y` | 基地 | (x, y) 上是敌方单位，距基地不超过 2 | 造成 10 伤害 |

**卸货不需要指令：** 回合结束时，凡是和己方基地或己方塔相邻的工兵，自动把携带的矿全部存入，变成能量。

### 4.4 结算顺序

两方的指令同时提交、同时结算。每一步内部同时生效，步骤之间按下面的顺序进行。

1. **校验。**
   - 不合规的指令作废，记一条警告，不判负。
   - 同一个单位有多条指令时，只保留第一条。
2. **攻击。**
   - 所有 ATTACK 和 FIRE 同时造成伤害，目标按回合开始时的位置确定。
   - 然后移除生命降到 0 及以下的单位和塔；塔被摧毁后，变回空塔基。
   - 被移除的单位，本回合的攻击已经生效，其他指令作废。
   - 如果有基地的生命降到 0 及以下，对局在这一步之后结束（见 4.5）。
3. **生产。**
   - 执行 SPAWN，扣能量。
   - 两方生产到同一格时，都失败，不扣能量。
4. **移动。** 按下面的顺序判断：
   1. 目标不是空地的移动，失败；
   2. 两个或更多单位要进同一格，都失败；
   3. 两个单位互换位置，都失败；
   4. 反复检查，直到不再变化：如果目标格里有一个不动的单位（它没有移动指令，或者它的移动已经失败），这次移动失败；
   5. 剩下的移动全部成功，包括三个以上单位的轮转。

   这一步生产出来的单位已经占住了格子，算作不动的单位。
5. **采矿。** 把同一个矿格上本回合所有合规的 MINE 放在一起结算。
   - 每个工兵想采的量 q = min(10, 60 − 携带量)。
   - 所有人想采的总量不超过储量时，每人得到 q。
   - 超过储量时，每人得到 min(q, ⌊储量 ÷ 人数⌋)，剩下的零头作废，这个矿格的储量变为 0。
6. **卸货。**
   - 和己方基地或己方塔相邻的工兵，把携带的矿全部转为能量。
   - 卸下的量同时计入这一方的"累计卸货量"。
7. **建造。**
   - 执行 BUILD，扣能量，可以用本回合刚卸下的能量。
   - 两方在同一回合、同一个塔基上建塔：都失败，不扣能量。
   - 同一方几个工兵建同一个塔基：编号最小的那个执行。
   - 同一方有几条 BUILD 时，按单位编号从小到大扣能量，钱不够的失败。
8. **回复。** 距己方基地 2 以内的己方单位回复 5 生命，不超过上限。
9. **计分。** 每方加上自己现有的塔数。

**没有任何一条规则偏向某一方。** 冲突的处理一律对两方同时生效。单位编号只在同一方内部排先后。

### 4.5 胜负

- **基地被摧毁：** 攻击之后，只有一方的基地被摧毁，这一方输；两方同时被摧毁，平局。
- **到了回合上限：** 按下面的顺序比较，前一项相同才比下一项：
  1. 分数高的赢；
  2. 累计卸货量多的赢；
  3. 基地生命多的赢；
  4. 都相同，平局。
- **出错：** bot 崩溃、超时（6.2）或编译失败，这一局判负；两方在同一回合都出错，平局。
- **不能靠"不动"拿平局：** 什么都不做的 bot，输给任何会采矿的 bot，因为它的累计卸货量是 0。

### 4.6 设计意图：几条路线，以及怎样互相克制

A 阶段要用策略动物园验证这些关系（第 10 节）。

| 路线 | 长处 | 被什么克制 |
|---|---|---|
| 速攻：早出战士，直扑基地 | 打垮只发展、不设防的对手 | 有反应的发展打法：基地射击、回复、离家近，每回合还能补一个兵 |
| 发展：多造工兵，后期出兵 | 经济最强 | 速攻；骚扰工兵 |
| 守家：兵力留在基地附近 | 防得住速攻 | 塔分：不出门就没有塔 |
| 铺塔：工兵到处建塔 | 早期塔分多 | 塔会被拆，没有兵就守不住 |
| 骚扰：打工兵，拆远处的塔 | 拖慢对方经济 | 集中兵力的正面推进 |

几个关键机制：
- **塔既是计分点，也是卸货点。** 在矿区旁边建塔，运输距离变短，这就是"开分基地"，值得争夺。
- **家门口的矿有限**（约 2,400），中期必须向外扩张。远处的矿多，但暴露在外。
- **防守方有优势：** 基地射击、回复，加上每回合能补一个兵。所以小规模偷袭很难直接拆掉基地，要靠赢下大规模交战。
- **完全信息：** 双方的单位、能量、分数都看得见，所以可以识别对方的打法并调整。
- **战斗同时结算：** 按回合开始时的位置结算，伤害同时生效。集中火力（从四个方向围攻一个目标）、走位、选择交战的时机，都会影响结果。

附录 B 用默认数值估算了经济和攻防的时间线，说明这些关系在数值上大致成立。

## 5. bot 协议 v1

### 5.1 进程

- 每局为每个 bot 启动一个进程，一直运行到对局结束。
- 引擎通过标准输入发消息，bot 通过标准输出回复。都是 UTF-8 文本行，以 `\n` 结尾。
- 标准错误输出：本地工具会显示出来（每局最多 64 KB），评分时丢弃。
- bot 必须是单进程。可以开有上限的多线程，但所有线程的 CPU 时间都计入用时（6.2）。回复 `END` 之后继续运行也计时，计入下一回合（D2、D3）。

### 5.2 开局消息

```
HRW 1                        协议版本
RULESET standard-1
```

## 6. 运行：安全、稳定、高效

### 6.1 沙箱

所有 bot 都只在沙箱里运行，包括被测模型的提交、阶梯 bot 和动物园 bot。

**评分和校准：** 每个 bot 进程一个 bubblewrap 沙箱，和 AgentEvalLab 的 `scripts/sandbox_exec.py` 用的参数一致：

```
bwrap --unshare-all --die-with-parent --new-session --cap-drop ALL --proc /proc --dev /dev --tmpfs /tmp
      --ro-bind-try /usr /usr  （/bin /sbin /lib /lib32 /lib64 /libx32 同样只读挂载；不挂载宿主 /etc）
      --ro-bind <Python 运行环境的安装目录>
      --ro-bind <这个 bot 自己的目录>
      --setenv HOME /tmp（TMPDIR、TMP、TEMP 同样设为 /tmp）
      -- <启动 bot 的命令>
```

- 没有网络；单独的 PID、IPC、UTS 命名空间。
- 系统目录只读。只挂载这个 bot 自己的目录（只读）和私有的 /tmp，看不到其他 bot 的文件。这一点对隐藏阶梯很关键：被测模型的 bot 读不到阶梯 bot 的代码。
- 资源上限：
  - bot 运行时地址空间 512 MiB（RLIMIT_AS）；C++ 编译时放宽到 2 GiB（D2）；
  - 单文件 16 MiB（RLIMIT_FSIZE）；`/tmp` 总量不超过 64 MiB，超过算 bot 出错。若实现选择只读 `/tmp`，必须在给模型的规则及本地工具中明示，不能成为仅评分时出现的隐藏限制（D2）；
  - 打开文件 64 个；
  - 整局 CPU 的硬上限（RLIMIT_CPU），按回合数折算，再加余量。
- 每个 bot 绑定一个独占的 CPU 核；bot 不能自行改变绑核。强制单进程，可以开有明确上限的线程，具体上限和限制方式写进规则；不能只依赖启动时默认 affinity 或按进程的 RLIMIT_CPU（D2）。
- 对局结束，结束 bwrap 进程，命名空间里的进程随之全部结束。

**被测模型工作区里的本地工具：** 工作区的每条命令已经在 AgentEvalLab 的沙箱里运行，不能再嵌套 bwrap。这台机器上已经验证：嵌套时 bwrap 报 "No permissions to create new namespace"。所以本地工具用"直接启动"（plain 启动器）：资源上限照设，只是没有文件隔离。

**启动器接口：** 启动器做成接口，有 bwrap 和 plain 两种实现。评分和校准只允许用 bwrap。

**C++ 编译：** 也在沙箱里进行，命令是 `g++ -O2 -std=gnu++20 -I/sdk -o bot *.cpp`（GCC 11，只用标准库）。按 `inbox/2026-11-07-phase-a.md` 第一节裁定：任务数上限16；每进程地址空间2 GiB、单文件64 MiB；墙钟与CPU上限均60秒。全机部署使用同一用户与共享锁目录，同一时间只编译一个，缓存命中不再编译。工具链顺序执行，不执行提交方程序；不要求cgroup或宿主配置改动，不声称这些逐进程限额是整树内存/磁盘硬配额。

**提交格式（M6）：** 目录含 `main.py`，或顶层一个以上 `*.cpp`，二者只能选一种。不得含符号链接或特殊文件；单文件不超过 16 MiB、总量不超过 64 MiB。被测提交不合规按编译失败判负，保留明确原因；隐藏阶梯或地图配置不合规属于配置错误，不算提交方输。`check` 使用相同校验。

### 6.2 计时

**按 CPU 时间计，不按墙钟。** 不受其他进程抢占 CPU 的影响；频率变化、共享核和负载引起的有效算力差异，必须用同并行度的速度折算处理，不能认为 CPU 时间不受负载影响（D4）。

**怎么测（在这台机器上实测过）：**

| 来源 | 结果 |
|---|---|
| `/proc/<pid>/schedstat` | 这个内核上读出来是 0，不能用 |
| `/proc/<pid>/stat` | 只有 10 毫秒的精度 |
| 进程的 CPU 时钟：`clock_gettime`，时钟号 `((~pid) << 3) \| 2`；Python 里是 `time.clock_gettime_ns(((~pid) << 3) \| 2)` | 能读到纳秒精度，已验证。**采用这个** |

- 运行器在每回合收到 `END` 时读一次累计 CPU。本回合用时 = 这次读数 − 上次读数。第一回合的起点是收到 `READY` 时。回复 `END` 之后继续运行的 CPU，计入下一回合（D3）。
- bot 强制单进程，进程 CPU 时钟包括全部线程；不能漏记线程退出前的用时。用 `/proc/<pid>/task/<tid>/children` 定位跨命名空间的 bot，启动后找不到 bot 进程或无法可靠计量时应报框架错误，不能静默只读到 bwrap。
- 跨 bwrap 的 PID 命名空间读取，在这台机器的 AI 沙箱里没法测（嵌套 bwrap 不可用），A 阶段要在真实环境里验证。不行就退回 `/proc/<pid>/stat`，并在报告里说明。

**时限：**
- 每回合 100 毫秒。超出的部分，从每局 3,000 毫秒的时间储备里扣；储备扣到负数，判超时负。
- 开局初始化 2,000 毫秒，不扣储备。
- 墙钟兜底：一回合的墙钟时间超过"本回合时限 + 剩余储备 + 500 毫秒"，也判超时负，防止 bot 卡在读写上。

**按机器速度折算：**
- 同一个 bot 在更快的 CPU 上会更强，所以框架带一个固定的单核基准程序（C++，确定性的计算）。
- 速度系数 = 现测用时 ÷ 参考用时。参考用时是评测机器空闲时单实例的结果。
- 每次评分和校准开始时，`bench --jobs N` 同时在 2N 个绑定的 CPU 上运行同一基准，取中位数；测量和实际运行并行度一致，评分和校准期间保持并行度不变（D4）。
- 时限、时间储备、墙钟兜底和 CPU 硬上限都乘速度系数。评测机器满负荷时系数也不再固定为 1.0。
- 折算后的时限、参考基准、并行度和速度系数写进每局回放的文件头。
- 阶梯仍以评测机器上的校准为准（11.4）。

**记录：** 每回合的 CPU 时间和墙钟时间都记进回放，用于诊断。

### 6.3 出错的处理：分清"bot 的错"和"框架的错"

| 情况 | 算谁的 | 处理 |
|---|---|---|
| 编译失败、启动后不回 READY、进程退出、超时 | bot | 这一局判负 |
| 格式错误的行、非法指令 | bot | 作废，记警告，不判负 |
| 沙箱准备失败（运行器没有收到启动标记）、运行器异常、机器资源不足 | 框架 | 这一局作废重跑，最多 3 次。仍然失败，就标记为"框架错误"，不计入任何一方的成绩，并在报告里列出 |

启动标记之后的任何退出都算 bot 的错，不看退出码；不能把 bot 的退出码 125 当成沙箱准备失败（D7）。

引擎本身在任何情况下都不能因为 bot 的输出而崩溃：解析有长度上限，更新状态之前先校验。

### 6.4 效率目标

| 指标 | 目标 | 在哪里测 |
|---|---|---|
| 引擎每回合（80 个单位，40×40 地图） | p95 不超过 2 毫秒 | A 阶段，写进 data/timing.json |
| 运行器每回合的开销（不含 bot 思考） | p95 不超过 3 毫秒；最大值另报，不作门槛 | A 阶段 |
| 一局（两个 bot 都用满折算后每回合时限，300 回合） | 不超过 300 × 折算后每回合时限 + 5 秒 | A 阶段 |
| 一次完整评分（约 500 局） | 评测机器上平均不超过 45 分钟 | C 阶段 |

上述口径由 `inbox/2026-11-07-phase-a.md` 第一节解释：原35秒是100ms不折算时的特例，5秒是框架余量；折算后的整数毫秒时限以实际LIMIT为准。不是降低平衡门槛。

- **并行：** 每局的两个 bot 各占一个核，运行器很轻。评测机器默认同时跑 6 局，用 12 个核、约 6 GB 内存，给系统留出余量。并行数可以配置。
- **调度器：**
  - 一批对局写成任务清单，每个任务是 (bot A, bot B, 地图, 先后手, 种子)；
  - 结果追加写入结果库（JSONL）；
  - 已经完成的任务跳过，中断后可以续跑。
- **可读性：** 引擎要高效，但不能牺牲可读性，被测模型会读它来理解规则细节。

## 7. 地图

### 7.1 生成器

- 自带伪随机数生成器（例如 PCG32 或 SplitMix64，用纯 Python 实现），不用 Python 的 `random` 模块。这样以后任何 Python 版本生成的地图都一样。
- 地图类型：开阔、走廊、岛屿（几块区域由窄通道连接）、迷宫。每种类型有自己的参数，比如墙的密度、通道的宽度。
- 先生成半张地图，再旋转出另一半，保证对称。

### 7.2 生成后的检查

不合格就换一个种子重新生成。

1. 所有空地连通；两个基地之间的最短路长度至少是 1.2 × max(W, H)。
2. 每个基地附近（曼哈顿距离 4–8）有一片家门口的矿，约 6 格，共约 2,400；每格矿的步行距离不超过 12 步。步行距离是从基地的相邻空地走到矿格相邻空地的最短步数（D5）。
3. 中间地带的矿更多：每方约 6,000，中心区另有两方共享的约 6,000，离基地更远。
4. 塔基 8–12 个，对称分布，至少一半在矿区附近：曼哈顿距离 3–5，并且从塔基的相邻空地走到矿格的相邻空地不超过 6 步（D5）。
5. 卸货点（基地、塔基）和任何矿格之间的距离至少是 3，所以工兵在采矿和卸货之间至少要走一步。
6. 每个基地周围距离 2 以内的空地至少 8 格，保证有地方出兵。

### 7.3 地图集

| 地图集 | 用途 | 是否公开 | 数量（v1） |
|---|---|---|---|
| public | 被测模型在本地测试 | 公开 | 40，四种类型各 10 张 |
| scrimmage | 中场练习赛 | 公开 | 4 |
| calibration | 阶梯校准 | 隐藏 | 24 |
| grading | 评分 | 隐藏 | 24，四种类型各 6 张 |

- 地图用文本文件保存。评分和校准读文件，不现场生成，所以以后改了生成器，也不影响已经发布的版本。
- 隐藏的地图集放在 `private/`，只公开 sha256。

## 8. 回放和存档（为以后的可视化留接口）

### 8.1 格式

- 每局一个文件 `<对局号>.hrw.jsonl.gz`，是 gzip 压缩的 JSON Lines。
- **第 1 行，文件头：**
  - 回放格式的版本、引擎版本；
  - ruleset 和全部参数；
  - 地图全文和它的 sha256；
  - 双方 bot 的代号和 sha256、种子；
  - 折算后的时限、速度系数、开始时间。
- **每回合一行：**
  - 回合号；
  - 双方被接受的指令；
  - 作废的指令及原因；
  - 双方的 CPU 用时和墙钟用时；
  - 本回合结束后的状态哈希。
- **最后一行，结果：** 胜负、原因、回合数、双方的分数、累计卸货量、基地生命、超时和警告的次数。
- 估计每局压缩后 30–60 KB。

### 8.2 用法

- **重放：** 引擎是确定性的，有文件头和每回合的指令，就能重放出每一回合的完整状态，再用状态哈希核对。

  注意：如果 bot 按时间决定思考多深，重新打同一局，结果可能不同；但回放记的是指令，所以总能精确重放。
- **以后的网页回放器：** 例如用 JavaScript 重新实现结算。也用同样的状态哈希来验证它和引擎一致。
- **工具：**
  - `replay show`：某一回合的 ASCII 棋盘；
  - `replay summary`：每 25 回合的关键数据，包括能量、单位数、塔数、分数；
  - `replay verify`：重放并核对哈希。
- **存档：**
  - 用户的开发机器有 3 TB 硬盘，可以保留全部对局。
  - 评测机器上，评分对局的回放放在 AgentEvalLab 的 `runs/archive/ca/` 下，按任务版本和提交分目录；结果的汇总永久保留。
- **格式本身也是约定：** 用版本号管理；改格式只能加字段。

## 10. 防退化与平衡（A 阶段）

### 10.1 策略动物园

| 代号 | 打法 |
|---|---|
| Z-idle | 什么都不做 |
| Z-random | 随机的合法指令 |
| Z-miner | 只采矿，不出兵，不建塔 |
| Z-rush | 开局全出战士，直扑基地 |
| Z-wrush | 工兵速攻 |
| Z-eco | 先铺满工兵，后期出兵推进 |
| Z-turtle | 兵力守在基地附近，只采家门口的矿 |
| Z-towers | 工兵到处建塔，几乎不出兵 |
| Z-harass | 小队打工兵、拆远处的塔 |
| M-balanced | 兼顾经济、建塔、出兵，按对方的兵力调整。这是中等强度的参照 bot，公开，以后放进 L2 |

### 10.2 验收指标

每对 bot 打完全部 40 张 public 地图，每张交换先后手各一局，共 80 局。区间按地图 bootstrap，一起报告；相同地图、位置和种子的确定性重复不能充当新样本（D6）。

1. **没有通吃的单一打法：** 每个单一打法（Z-* 里除去 idle 和 random）至少输给另一个单一打法，即胜率低于 50%。
2. **兼顾型占优：** M-balanced 对每个单一打法的胜率至少 70%，在每种地图类型上都至少 55%。
3. **先后手公平：** 在所有不同 bot 之间的对局里，同一个 bot 做 0 号和做 1 号的得分率相差不超过 3 个百分点，而且 95% 区间包含 0。

   同一个确定性的 bot 自己打自己，在对称地图上会是平局，这是正常的，所以公平性用不同 bot 之间的对局来检查。
4. **平局率：** 除 Z-idle 以外且不同名 bot 的对局，平局低于 10%。
5. **对局长度：** M-balanced 必须用 `SEED` 派生少量开局和时机参数，强度不变；“M-balanced 之间”指两个不同种子的实例。长度的中位数至少 120 回合；60 回合内就结束的，低于 20%。
6. **两种结束方式都要有：** A 阶段只看上述不同种子 M-balanced 实例之间的对局，拆基地结束和比分数结束各占 20%–80%；B 阶段再加入更强的 bot 复查（D6）。
7. **地图类型：** 按类型分别报告胜率矩阵；不能有某种地图上，某个单一打法赢 M-balanced。
8. **确定性：** 同样的地图和指令序列，状态哈希逐回合相同；回放可以完整重放。
9. **对称：** 把一局的两方对调、地图旋转 180°，结果和事件也对称。
10. **健壮性：** bot 输出乱码、超长行、非法指令，或者崩溃、死循环，引擎和运行器都能正确处理（判负或记警告），自己不崩溃。

### 10.3 调参流程

- 只能调附录 A 列出的参数，而且在给定的范围内。
- 每次改一两个参数，重跑动物园矩阵，把改了什么、为什么、依据的数据写进 `rules/CHANGELOG.md`。
- 要改规则本身（加机制、改结算顺序、改胜负条件），先在 STATUS.md 里提出，等评测负责人同意。
- 所有指标都达到后，把参数冻结为 `standard-1`，A 阶段结束。

## 11. 对手阶梯（B 阶段）

### 11.1 构成

- **级数：** 约 12 级，L0 到 L11。每级是一个"小组"，放 2–3 个强度相近、风格不同的 bot。
- **风格：** 至少三种：
  - 进攻（a）：早压制，逼对方交战；
  - 经济（e）：扩张，后期大军；
  - 控制（c）：抢塔、守点、骚扰。
- **间距：** 相邻两级相差 100–150 Elo，也就是下一级对上一级的胜率约 30%–36%；同一级里的 bot 相差不超过 ±40 Elo。

| 级 | 内容 | 是否公开 |
|---|---|---|
| L0 | Z-random、Z-miner | 公开 |
| L1 | 单一打法里较强的几个，例如 Z-rush、Z-eco、Z-towers | 公开 |
| L2 | M-balanced 和其他简单的规则 bot：会采矿、建塔、出兵，配比固定 | 公开 |
| L3–L5 | 有计划的启发式 bot：任务分配、影响力图、简单的局部战斗估计 | 隐藏 |
| L6–L9 | 强 bot：局部战斗模拟或搜索；识别对方打法并调整；按地图选择路线 | 隐藏 |
| L10–L11 | 最强的 bot：astra 用多轮会话长时间开发，并用大量自我对弈调参 | 隐藏 |

- **强度档：** 同一种风格的强 bot，可以用限制算力（只用时限的一部分）或去掉部分功能的办法，做出几个强度档，填进不同的级。但每一级里的几个 bot 要来自不同的风格。
- **同样的限制：** 阶梯 bot 和被测模型的提交受同样的时限和资源限制。高级 bot 强在算法和离线调好的参数，不在运行时的算力。

### 11.2 作者多样化

- v1 的阶梯主要由 astra 写，这是一个已知的局限：astra 被测时，可能因为"和自己的写法相近"而系统性地占便宜或吃亏。
- 对策：
  - 每级的几个 bot 风格不同；
  - 试跑以后，把其他模型（sol、deepseek 等）的最好提交加进阶梯（11.6）；
  - 报告按 bot 分项列出成绩，这种偏差可以看出来。

### 11.3 公开和隐藏

- L0–L2 的源码随任务公开，给被测模型当陪练，中场练习赛也用它们。
- L3 及以上隐藏：源码和编译产物只放在 `private/`，不进公开仓库，也不出现在任何公开的回放里。
- 规则文档写明阶梯有几级、每级大致是什么打法（9.3），但不写具体实现。

### 11.4 校准

- **对局：** 在 calibration 地图集上，阶梯的 bot 两两对局，范围是：
  - 同一级里全部配对；
  - 相邻两级之间全部配对；
  - 相隔一级的全部配对。

  每对 24 张图，交换先后手，共 48 局。总共约 230 对、1.1 万局，按每局 20 秒、8 局并行估计，约 8 小时。
- **拟合：** 用 Bradley–Terry 最大似然拟合 Elo，平局算半胜。L0 的平均 Elo 固定为 0。按地图做 bootstrap，求区间。
- **省局数：** 用序贯检验（SPRT）判断相邻两级的间距。相隔一级的配对，明显超过 200 Elo 就可以提前停。
- **迁移后在评测机器上复核：**
  - 相邻两级的配对重新打一遍，每对 24 局；
  - 间距和单调性要和原来一致，容差 ±50 Elo；
  - 不一致就以评测机器的结果为准，重新拟合。

### 11.5 阶梯的验收

1. **单调：** 每一级的平均 Elo 都高于下一级，相邻间距在 80–200 之间。
2. **同级接近：** 同一级里 bot 的差距不超过 80 Elo。
3. **没有"隔级反胜"：** 任何 bot 对比它高两级的 bot，胜率低于 40%。
4. **风格：** 每一级至少有两种风格。
5. **可钻空子的程度：**
   - astra 开一个新会话，能看到阶梯的代码，专门写一个针对阶梯的 bot，但不能复制阶梯 bot 的代码；
   - 再开一个新会话，同样的预算，只用公开材料写一个 bot；
   - 两者的主分数相差不超过 0.15。超过了，说明阶梯有固定的漏洞，要增加多样性或随机性。
6. **标准预算自测（检查阶梯顶端够不够强）：**
   - astra 按正式任务的流程和预算写一个 bot：两个阶段，每个阶段一个新会话，只用公开材料；
   - 工作区里没有 `private/`，没有这个仓库的历史和笔记；
   - 评分后，主分数应该不超过 0.6；超过了，就继续加强顶端；
   - 自测的提交不放进阶梯。
7. **防“一招鲜”（用户2026-11-08决定）：**
   - 将动物园的9个Z bot和M-balanced逐个作为提交，对L6及以上的每一级打校准对局，计算每一级的平均得分。
   - 只用胜负分：胜1、平0.5、负0，不使用过程分雏形。
   - 每个bot在L6及以上每一级的平均得分不超过0.1；具体数值按B阶段数据在审查时确认，构建者不得自行放宽门槛。
   - 不达标时加强相应阶梯，例如增加能克制该打法的bot，不能靠降低要求通过。
   - 公开报告只写允许公开的代号与统计，不披露哪个隐藏bot输给了哪种具体打法。
8. **留出复核，必须在建阶梯之前完成（用户2026-11-08决定）：**
   - 先生成隐藏calibration和grading地图；用24张calibration地图，对冻结的动物园v15跑一轮与D6相同的矩阵：每对24张图、两个座位，种子17/29；包含不同种子M-balanced自对弈，以复查结束方式。
   - 重新检查10.2的第1、2、4、6、7条。按地图簇报告区间，不能把确定性重复当成新样本。
   - 公开报告只写汇总统计，不写逐图结果、地图内容或生成种子；地图及原始对局只放private/。
   - 任何要求不达标，先停下来报告并提出重新调参方案，不继续建阶梯或擅自重抽地图。后续获准调参时仍只在附录A范围内，每次同时重跑公开与calibration两套完整矩阵。

### 11.6 更新（"对照组"）

- 每一轮正式评测后，挑出最强的几个提交，经过同样的校准，作为下一个版本的新级，放在阶梯顶端，或者补进现有的级。旧的级不变。
- 这就是"用量压缩"：模型变强了，阶梯也跟着往上长。

## 12. 计分

用户 2026-11-06 确认了两点：
- 主分数取各级得分的平均；
- 每局得分以胜负为主，适当加入过程分。

用户 2026-11-07 再次决定：过程分只是雏形，用于减少只看胜负的偏差，权重不宜高。下列公式、指标和权重不是当前要冻结的方案，不提前定公式或争论权重；等实际测试和大规模运行有数据后再补齐验证，评测负责人审查、用户确认后才冻结。现在结果库只需保留结束回合、结束方式和各项原始指标，支持事后重算。计分内容可留在公开构建仓库，但不进入给被测模型的材料（D8）。

### 12.1 每局得分

当前雏形：每局得分 = 0.75 × 胜负分 + 0.25 × 过程分（并非冻结公式）。过程分在全部对局结束后统一结算（D8）。

- **胜负分：** 胜 1、平 0.5、负 0。
- **过程分：** 0 到 1，衡量这一局里本方相对于对手的表现（12.2）。
- **胜负仍是主体：** 赢一局至少得 0.75，输一局最多得 0.25，所以赢永远比输得分高。过程分让"险负"和"惨败"、"险胜"和"完胜"有了区别，在胜负一边倒的级别上也能分出高下。
- **出错判负的局，过程分记 0：** 包括编译失败、崩溃、超时。

### 12.2 过程分的雏形

用三个"份额"指标，每个都是"本方 ÷（本方 + 对方）"，在 0 到 1 之间；两方都是 0 时记 0.5。

统计的范围是整局，从开局到结束；基地被拆的局，算到被拆的那一回合。拆基地获胜的局，过程分先记 1；这是雏形阶段的写法，以后可以改（D9）。

| 指标 | 计算 | 反映什么 | 默认权重 |
|---|---|---|---:|
| 塔分份额 | 本方的塔分 ÷ 双方塔分之和 | 控制地图，直接对应胜负条件 | 0.4 |
| 经济份额 | 本方的累计卸货量 ÷ 双方之和 | 发展 | 0.3 |
| 战斗份额 | 本方造成的伤害 ÷ 双方造成的伤害之和（对单位和建筑都算） | 交战的效率 | 0.3 |

**候选指标"存活"：** 本方基地存活的回合数 ÷ 回合上限，赢或平局记 1。要不要加入，由构建者用数据判断。

**为什么这里可以用局内数据：** 第 12.6 节说局内得分不可比，指的是对手不同的情况。这里不一样：
- 所有提交面对完全相同的对局，阶梯 bot、地图、先后手、种子都一样；
- 用的是"本方占双方的份额"，不受地图大小和对局长度影响。

所以不同提交的过程分可以直接比较。

### 12.3 补齐时的约束和验证（构建者做）

**约束：**
1. 过程分的总权重在 0.2–0.3 之间，默认 0.25。
2. 只用引擎已经记录的数据，能从回放重新算出来。每局的各项指标都存进结果库，以后调权重直接重算，不用重打。
3. 指标都是两方对称的份额，不用绝对数值。
4. 不能奖励和取胜冲突的行为，例如为了刷经济份额而不去赢。

**验证：** 用 B 阶段校准对局的数据，在 C 阶段完成，结果写进 phase-C 报告。
1. **和强度一致：** 每个阶梯 bot 对固定对手组的平均过程分，和它的 Elo 做秩相关，相关系数至少 0.9。
2. **防刷分：** 动物园里的单一打法，尤其是 Z-turtle、Z-miner、Z-towers，对同一组对手的平均过程分，不能高于 M-balanced。哪个指标能被单一打法刷高，就降低它的权重，或者换掉。
3. **有用：** 用"只看胜负"和"加过程分"两种算法分别评分，比较相邻两级 bot 的主分数差距和标准误。加了过程分，区分应该更清楚。
4. **提出方案：** 根据数据提出最终的指标和权重，不能超出上面的约束。

### 12.4 主分数

- 一级的得分 = 对这一级小组里每个 bot 的平均每局得分，再在小组内取平均。
- 主分数 = 所有级的得分的平均，在 0 到 1 之间。
- 例子：
  - L0–L5 全胜、L6–L11 全负，赢的局过程分平均 0.7、输的局 0.3：前 6 级每级 0.925，后 6 级每级 0.075，主分数 0.5。
  - 一个输掉所有对局、但过程分平均有 0.2 的 bot，主分数约 0.05，正好是弱模型的保底水平。

### 12.5 对局安排和精度

- **对局安排固定：**
  - 评分地图 24 张；
  - 提交和每个阶梯 bot 在指定的 7 张图上各打两局，交换先后手；
  - 每一级用 21 张图、42 局；12 级共约 500 局；
  - 所有提交面对完全相同的对局（同样的对手、地图、先后手、种子），所以提交之间可以成对比较。
- **精度：** 每一级 42 局，主分数的标准误约 0.02，95% 区间约 ±0.045。准确的区间按地图做 bootstrap 得出。

### 12.6 诊断，以及几个设计取舍

- **诊断（只报告，不计分）：**
  - 只看胜负的主分数，也就是不加过程分时的主分数；
  - 以阶梯为固定锚点的 Elo 和区间，只用胜平负计算；
  - 每一级的胜、平、负，以及过程分的各项指标；
  - 得分过半的最高一级；
  - 超时、崩溃、警告的次数，平均用时；
  - 胜负原因的分布。
- **为什么不直接用局内的绝对得分：** 塔分、能量的绝对值都取决于对手是谁，换了对手就没法比。所以只用固定对局上的胜负，加上两方对称的份额（12.2）。
- **为什么不只报"击败的最高一级"：** 那只是一个越线点，受运气影响大；各级平均用上了所有对局，更稳定。
- **联赛（只报告，不计分）：** 每一轮结束后，所有模型的提交和阶梯一起打循环赛，得出"哪个模型写的 bot 最强"的表，也用来挑选下一个版本的新级。
- **第一阶段的提交：** 也评分，只作诊断。两个阶段的分差，反映模型能不能从对局结果里学到东西。

## 13. 任务流程和预算（在 AgentEvalLab 里运行）

被测模型全程不联网，只能用工作区提供的内容写 bot、测试和评价（D10）。构建者开发本项目可联网查文档资料，仍不得让对局和 bot 运行联网；框架只用标准库，安装新工具先问用户。

| 阶段 | 内容 | 预算（试跑后校准） |
|---|---|---|
| 第一阶段：设计和实现 | 读规则；写出能用、经过测试的 bot；可以用公开对手、公开地图和本地工具；笔记写在 NOTES.md | 约 6M token、2.5 小时 |
| 中场练习赛（框架自动执行，不调用模型） | 第一阶段的提交对 3 个公开 bot，在 2 张 scrimmage 地图上各打两局（交换先后手），共 12 局 | 约 3 分钟 |
| 第二阶段：优化 | 新会话；读自己的代码、NOTES.md 和练习赛的结果，改进 bot | 约 8M token、3 小时 |

- **练习赛的对手：** 只用工作区里已有的公开 bot，不和隐藏阶梯打，也不和其他模型的提交打（用户的决定）。默认是 L2 小组里的 bot，不够 3 个时用 L1 里最强的补上，C 阶段定下来。
- **练习赛的结果** 写进工作区的 `scrimmage/`：
  - 战绩表：每个对手、每张图的胜平负、结束原因、最终局内比分，以及超时、崩溃和警告次数；不提供过程分及其指标或其他计分细节（D8）；
  - 每局每 25 回合的关键数据；
  - 输得最惨的 3 局的完整回放。
- **起点：** 工作区里的 `bot/` 一开始是空的（示例 bot 在 sdk/ 里，模型可以自己复制），所以分数只反映模型自己做的事。
- **最终提交：** 第二阶段结束时 `bot/` 里的内容。
- **预算的校准方法：**
  - 第一阶段：测"做出第一个能用的 bot 要多少预算"，定在常用模型里有 80% 以上能做出能用的 bot 的位置；
  - 第二阶段：每 1M token 给 bot 拍一个快照，事后用部分对局评分，画出"强度随预算"的曲线，定在最强模型的提升趋于平缓之处的约 1.5 倍。
- **分工：** AgentEvalLab 一侧的改动（阶段之间的练习赛、快照、评分器的包装）由评测负责人做；这个仓库提供可以直接调用的命令（第 14 节）。

### 14.3 自检（C 阶段，结果写进 logs/self-calibration.log）

## 15. 版本和扩展

### 15.1 版本

| 对象 | 版本号 | 规则 |

## 16. 公开与保密

这个仓库（GitHub 上的 AgentEvalLab-HumanRaceWar）是公开的，评测负责人用普通的 HTTPS 拉取。所以：

  `private/` 在 .gitignore 里，永远不提交、不推送。
- **公开的报告和数据里**，隐藏 bot 只写代号、风格标签、sha256 和统计数据，不写实现细节，也不写它的弱点。
- **上传范围（用户2026-11-08补充）：** GitHub只保存审查所需代码、配置、测试、文档和汇总；实际对局回放、逐局结果、结果库与逐局审计索引均留在开发机。公开bot示例回放也不上传。所有失败照常完整保留在本机，不改变统计分母。
- **不提交任何凭据、令牌和个人信息。**
- **提交前检查：** 仓库带 `.githooks/pre-commit`，拒绝以下内容：
  - `private/` 和 `runs/` 下的文件，以及实际对局回放、逐局表和逐局索引；
  - 超过 2 MB 的文件；
  - 看起来像凭据的文件；

- **万一隐藏内容被推送了：**
  - 立即告诉用户；
  - 那个 bot 或那张地图作废（降为公开），换新的；

## 附录 B：原始起点的数值估算（历史）

以下使用调参前的初始数值和32×32地图，解释当时的设计假设，不是当前standard-1的数值说明；A阶段已用完整矩阵检验并调整，当前值见附录A。

### 经济

- **一个工兵的收入：** 采满 60 要 6 回合，往返各走约 4 步，一趟约 14 回合，所以每回合约 4.3 能量。造价 50，约 12 回合回本。
- **有塔的时候：** 在离矿 3 格的地方建塔，一趟缩短到约 10 回合，每回合约 6 能量，所以在矿区旁建塔值得。
- **家门口的矿：** 共 2,400。8 个工兵每回合约采 34，大约 70 回合采完，所以第 70–90 回合前后必须向外扩张。

### 速攻

- **兵力：** 速攻方第 1–3 回合造 3 个战士，把能量用完；之后只有 2 个工兵的收入，每 12 回合左右才能再补一个兵。
- **到达时间：** 两个基地之间的路至少 1.2 × 32 ≈ 40 步，第一波大约第 43 回合到达。
- **对有反应的发展方：** 这时发展方已经攒了约 700–900 能量，可以每回合在基地旁补一个兵，加上基地射击（每回合 10）和回复（每回合 5），速攻失败。
- **对不设防的发展方：**
  - 3 个战士每回合打 60；基地每 10 回合打死一个战士；
  - 前 10 回合打掉 600，再 10 回合打掉 400；
  - 约 20 回合拆掉基地。

  所以速攻能赢贪发展的对手，输给会反应的对手。这正是 4.6 想要的克制关系。

### 塔和分数

- 塔造价 150。第 60 回合建成的塔，到第 300 回合最多得 240 分。
- 塔的生命 300：4 个战士围攻（每回合 80），4 回合就能拆掉；1 个战士要 15 回合。所以一个兵偷塔，对方来得及支援。
- 一局结束时的分数大约在 300–1,500 之间。
