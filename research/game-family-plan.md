# 策略编程游戏族：规划

本文的仓库事实都对照 2026-11-27 的 `main` 工作树核过，路径相对仓库根目录。所有数字都来自已公开的报告和聚合文件。

## 1. 目标

沿用 HRW 的做法做出 3–5 款游戏，每款主要考一种能力。被测模型在固定预算内为每款游戏写一个 bot，由该游戏的隐藏阶梯评分。报告分两层，先给每种能力上的成绩，再给总体成绩。这些游戏在模型之间要拉得开，不追求把模型难倒（用户原则：要的是区分度，不是击败模型）。

## 2. 从 HRW 带过来的方法（逐项核对）

还有几项背景里没列、也值得带走的要素：

- **预登记，然后只用一次。** 最终留出先在 `docs/RELEASE_HOLDOUT_PREREGISTRATION.md` 登记，再只跑一次，结果不理想也不重跑（DESIGN 11.5 第 8 条）。
- **防"一招鲜"检查。** 每个公开 bot 对高级别的平均得分不得超过 0.1（DESIGN 11.5 第 7 条）。
- **知情组对盲组。** 让一组会话先看到阶梯相关信息，比较两组主分，量出阶梯能被钻空子的程度（第 5 条）。
- **回放能逐字节复现。** 引擎升到 1.0.0 后，重放 104 份旧回放，29,404 回合的状态和协议输出逐字节一致（`reports/phase-C.md`）。
- **发布保护。** `.githooks/`、`tools/publication.py` 和 `tools/archive_round.py` 配合只追加的总账，防止隐藏字节进入公开树。

## 3. 哪些现成可用，哪些要泛化

DESIGN 3.1 的本意是"以后加第二款游戏，只需要写一个新的 `arena/games/<名字>/`，框架、阶梯、评分器全部复用"。`arena/core/game.py` 里确实有和游戏无关的 `Game` 接口，`Event` 也带了按玩家可见的 `audience` 字段，给战争迷雾留了口子。但调度层现在直接引用前哨。

**现成可用（基本不改）：**

| 部件 | 路径 |
| --- | --- |
| 沙箱启动、seccomp、外层沙箱专用的 plain | `arena/core/sandbox.py`、`sandbox_exec.py`、`seccomp.py`、`plain.py` |
| CPU 和编译锁 | `arena/core/resources.py` |
| 测速、计时锁、机器指纹 | `arena/core/benchmark.py`、`arena/bench/main.cpp`、`arena/core/timing.py`、`arena/core/machine.py` |
| 进程通信、逐进程 CPU 时钟、行长度上限 | `arena/core/transport.py` |
| 加锁并 fsync 的结果库，gzip JSONL 回放写入 | `arena/core/journal.py`、`arena/core/replay.py` |
| Bradley–Terry 拟合，按地图簇 bootstrap，处理分离 | `tools/provisional_bt.py` |
| 噪声评分、冻结锁、作者交付验收、回放审计 | `tools/release_noise.py`、`tools/freeze_release_timing.py`、`tools/receive_author_delivery.py`、`tools/audit_replays.py` |

| 发布检查和归档 | `.githooks/`、`tools/publication.py`、`tools/archive_round.py`、`docs/ARCHIVING.md` |
| 流程 | A/B/C 三阶段各自停下交审（DESIGN 17），预登记，`inbox/` 审查记录 |

**要泛化：**

| 位置 | 现在写死了什么 | 要改成什么 |
| --- | --- | --- |
| `arena/match.py` | 直接构造 `Outpost`，用前哨的 `Metrics` 和 `outcome` | 按回放头里的 `game` 字段查游戏注册表，每款游戏提供自己的 Game、指标和回放适配器 |
| `arena/tournament.py`、`arena/check.py`、`arena/__main__.py` | 引用前哨的 `Outpost`、`Rules`、`parse_map`、`verify`、`mapgen` | 同上，改走注册表 |
| `arena/scrimmage.py` | 对手 `Z-eco`/`Z-harass`/`Z-miner` 和两张图写成常量；`turns.csv` 用前哨字段 | 每款游戏的配置文件给出练习赛对手、地图和快照字段 |
| `arena/ladder.py` | ruleset 必须是 `standard-1`；版本号限 `1.0.x`；级数只允许 (12, 26) 或 (13, 28)；grading 24 张、calibration 12 张；每成员 7 个槽位；种子 [17, 29]；锚点代号 `M-balanced` | 每款游戏一份阶梯模式文件，写明这些参数；锚点代号也在里面 |
| `arena/scoring.py`、`arena/scoring.json` | 指标固定为 tower/deposit/damage；份额按两人计算（`peer = 1 - seat`） | 每款游戏声明自己的对称份额指标；多人游戏改用名次类评分（第 5 节 G5） |
| `arena/grade.py` | `raw_game(..., 300)` 写死了 300 回合 | 从规则参数读取 |
| `arena/core/runner.py` | 每回合所有玩家同时回复；限额键只有 `TURN_CPU_MS`/`INIT_CPU_MS`/`BANK_MS`；`BANK` 行由运行器替换 | 支持轮流行动（游戏告诉运行器本回合轮到谁），限额键由游戏声明 |
| `arena/games/outpost/replay.py`、`metrics.py`、`mapgen.py`，`tools/generate_*_maps.py` | 前哨专用 | 每款游戏各写一份；回放校验"只执行引擎、从不执行 bot"的原则不变 |
| `sdk/` | 前哨协议 | 每款游戏一套 SDK，沿用文本行协议、未知关键字跳过、示例 bot 只会最基本的操作（`sdk/README.md`） |
| `package/` | 前哨的任务说明 | 按游戏生成，白名单分开审 |

前哨已经有变体规则集的先例：`rules/proto-energy-1.json` 和 `rules/proto-ranged-1.json` 经 `arena/games/outpost/rules.py` 加载，关掉变体时与 `standard-1` 逐字节一致（`reports/phase-B-depth-prototypes.md`）。新游戏的规则版本可以照这个做。

前哨游戏模块约 1,450 行（engine、mapgen、maps、metrics、model、orders、replay、rules 合计），`arena/` 的框架部分约 3,000 行。泛化本身不是大工程。贵的是第 4 节讲的阶梯。

## 4. 主要成本是阶梯，怎样做便宜

### 4.1 HRW 的阶梯花了多少

从 11 月 8 日 A 阶段通过、获准进入 B（`inbox/2026-11-08-phase-a-accepted.md`），到 11 月 26 日 1.0.0 带披露接受，用了不到三周。中间有 Claude 作者 r01–r18 多轮、GPT 线、DeepSeek 线，以及一次 Fable 加力的天花板实验。公开记录里的局数：

- 联合开发图 40,320 个唯一局（`STATUS.md`）；
- 正式校准 5,376 局，另加多次补测；
- 天花板实验 9,120 局；
- 两个深度原型 9,920 局；
- C 阶段 19,812 局，发布修正又打 5,614 局。

成本大头不在 CPU，在于反复开作者会话写出一档档强度合适、风格不同的 bot，再一轮轮校准和取舍。顶端最难：两轮加力作者只比标准提交强几十到一百多 Elo（`inbox/2026-11-25-ceiling-result-review.md` 第二节）。

### 4.2 便宜的办法

**(a) 通用搜索 bot，按搜索预算分级。** 适用于有前向模型、完全信息、每回合动作空间不大的游戏：

- 用 alpha-beta 或 MCTS，把节点数或迭代数翻倍形成一档档强度；
- 用确定的工作量分级，不用 CPU 时间分级，换机器也不会变；DESIGN 11.1 已经允许"限制确定的工作量（例如评估/节点数）"形成档位；
- 2–3 种评估函数当作风格，满足 DESIGN 11.1"每级 2–3 名、风格不同"的要求；
- 引擎是确定性的 Python，可以直接当前向模型；正式用的阶梯 bot 最好用 C++ 重写搜索核心，以免受时限限制。

局限有三点：

- 同一套搜索加不同预算，弱点往往相同，"一招鲜"检查（DESIGN 11.5 第 7 条）和非传递性要专门查（Spinning Tops，见 literature.md）；
- 同时行动、单位多的游戏（例如前哨）联合动作空间爆炸，朴素搜索不可用，这正是前哨要靠手写 bot 的原因；
- 隐藏信息游戏要用信息集或抽样确定化的搜索，强度增长慢，方差也大。

**(b) 手写 bot 只留给少数深的 RTS 类游戏。** 前哨这类游戏靠手写多风格 bot，整个题族里这样的游戏最多保留一两款。

**(c) BotzoneBench 的做法**（arXiv 2602.13214，详见 literature.md）：

- 0 级是随机合法着；
- 往上直接从 Botzone 平台现成的 bot 里挑，依据是平台上的 Elo 排名和对下一级的胜率；
- 相邻级胜率一般控制在 70%–90%；
- 每级尽量混合规则、搜索、监督学习、强化学习等不同实现，按可用数量放 1–4 个。

它便宜，是因为平台上本来就有大量分级的 bot。我们没有现成的平台，所以 (a) 是对应的替代品。

间距的换算：HRW 要求相邻级 80–200 Elo，约合 61%–76% 胜率；BotzoneBench 的 70%–90% 约合 147–382 Elo。台阶粗，所需级数就少，但分辨率低。

**(d) 用往届提交补中段。** DESIGN 11.6 设想"每轮正式评测后挑最强的几个提交，经同样校准加进阶梯"。这样补中段很便宜，但用户的规则是"加深游戏，不靠加级"（见第 8 节），所以往届提交只用来补中段密度，不当新的顶端。

**(e) 同一份强 bot 去掉部分功能形成档位**，也是 DESIGN 11.1 已允许的做法。

**建议的组合：**

- 搜索型游戏用 (a) 加 (e)，再配一两个手写的风格成员；
- 只有深 RTS 类用 (b)；
- 每款新游戏都设一个公开的中段锚点（相当于 M-balanced = 0），再配公开的动物园和防"一招鲜"检查；
- 校准和验收照搬 DESIGN 11.5 第 1–3、7 条和 11.4 的相邻复核。

## 5. 能力轴和候选游戏

每款新游戏只在一条轴上和其他游戏明显不同，其余方面尽量简单，免得一款游戏同时考很多东西。前哨的位置是：完全信息、两人同时行动、中等时程的经济加战斗，几乎不奖励多算。天花板候选每回合最多用 4.3 ms，上限是 61 ms（`inbox/2026-11-25-ceiling-result-review.md`）。

| 轴 | 一端 | 另一端 | 前哨在哪 | 候选 |
| --- | --- | --- | --- | --- |
| 信息 | 完全信息 | 隐藏信息 | 完全信息 | G1 |
| 时程和经济 | 短、战术为主 | 长、复利和规划为主 | 中等 | G2 |
| 对手建模和适应 | 对手固定 | 必须局内识别并利用对手 | 弱 | G3 |
| 每回合算力和搜索 | 多算无益 | 多算明显占优 | 多算无益 | G4 |
| 玩家数和谈判 | 两人零和 | 多人，可结盟 | 两人 | G5 |
| 规则发现 | 规则全知 | 本局参数要靠试探推断 | 全知 | G6 |

下面六款都是为本项目新拟的规则草图，不复刻任何商业游戏。数值等原型阶段再定（用户原则：原型阶段不定公式和局数，等数据）。

### G1 雾渠（信息轴）

- **规则草图：** 两人同时行动。网格上有运河网和若干码头，双方的驳船运货回己方仓库得分。对方的驳船位置只在己方灯塔或巡逻艇的视野内可见；闸门是公开的，可以设置；暗桩是隐藏的，可以布下。旧观测要 bot 自己记住。
- **考什么：** 侦察、对对方位置的信念、隐蔽和佯动。
- **为什么和别的游戏分得开：** 经济和战斗都保持简单，强弱主要取决于信息处理。
- **阶梯：** 抽样确定化的 MCTS 按迭代数分级，再配冒进、潜伏、侦察优先三种手写风格。
- **风险：** 单局随机性大，要更多局才能把区间压窄；CA 在 2026-11-25 正是因此暂缓了前哨的视野方案。观察过滤必须做泄漏测试：两份局面的可见部分相同，bot 收到的消息就必须逐字节相同。

### G2 长账（时程和经济轴）

- **规则草图：** 两人，1,000–2,000 回合，每回合动作很少：投资、选生产配方、定价。共享市场的价格由双方供给共同决定；设备会折旧，借贷要付利息。早投资有复利，晚期才变现。没有战斗。
- **考什么：** 长时程规划，权衡复利，预测价格。
- **为什么分得开：** 动作简单，没有战术，强弱主要来自规划。
- **阶梯：** 有前向模型，可以按滚动规划的视野和样本数分级，再配保守、激进扩张、投机三种手写风格。
- **风险：** 可能退化成两三个参数的调参题，CA 对前哨"能量激活塔分"原型的顾虑一模一样。原型要直接量"多花工夫能多赢多少"，并检查最佳固定策略是否落在网格边界上（参照 `inbox/2026-11-25-ceiling-result-review.md` 第四节的筛选办法）。

### G3 分兵（对手建模和适应轴）

- **规则草图：** 两人，一局 100 场，对手不变。每场有若干战场，双方同时分配兵力，类似 Blotto 型分配博弈；赢下的战场给资源，资源结转到下一场，战场的地形权重每场公开轮换。对手从公开的类型分布中抽取，具体是哪种不告诉 bot。
- **考什么：** 局内识别对手的倾向并加以利用，同时不被对手反利用。
- **为什么分得开：** 单场规则很简单，没有空间战术，分数主要来自建模对手。
- **阶梯：** 必须有会适应的成员（虚拟博弈、后悔匹配、贝叶斯类型推断），按记忆长度或样本量分级；否则只要针对固定分布写一个 bot 就能刷分。要用 Nash averaging 或 α-Rank 的思路检查阶梯有没有冗余成员。
- **风险：** 非传递性强，平均分对阶梯的组成很敏感；每级需要更多风格。

### G4 分水岭（每回合算力和搜索轴）

- **规则草图：** 两人轮流行动，完全信息，结算确定。每步把一个格子的高度升或降一级。若干水源每回合出水，按确定的规则流向最低的相邻格。每隔 k 回合，按各方盆地里的积水计分。分支因子中等，一步的后果要过几步才显现。
- **考什么：** 搜索、评估函数设计、把时限用足。
- **为什么分得开：** 前哨不奖励多算，这款要反过来。原型过筛的条件之一是：同一个 bot 时限翻倍，得分要明显上升。
- **阶梯：** 最便宜。alpha-beta 或 MCTS 按节点数分级，2–3 种评估函数当风格。
- **风险：** 如果太像下棋，模型可能直接搬一套通用搜索框架就拿高分，所以要让评估函数成为瓶颈，规则要新，没有现成的知识可搬。运行器要先支持轮流行动（第 3 节）。

### G5 盟约港（玩家数和谈判轴）

- **规则草图：** 四人同时行动，争夺资源区。每回合先有一个结构化的提案阶段：可以提交有约束力的交换合约，由引擎强制执行；也可以发表没有约束力的公开声明，只能用固定词汇。之后再行动。
- **考什么：** 结盟、判断信任、同时建模多个对手、选择背叛的时机。
- **两种模式的差别：** 写 bot 模式只有结构化消息；自然语言谈判只能放在实时对局模式里，成本见第 6 节。
- **阶梯：** 被测 bot 和三个阶梯 bot 同桌，桌位轮换。评分改用名次类模型（如 Plackett–Luce 或 TrueSkill 类）。锚点是一桌固定的公开 bot。阶梯成员手写：守约型、投机型、报复型。
- **风险：** 同桌三个阶梯 bot 之间的互动也会左右结果（"造王者"效应），所以要很多桌，方差大。这是六款里最贵的一款。

### G6 未知星区（规则发现轴）

- **规则草图：** 两人。每局的参数从一个公开的规则族里抽，例如单位之间的克制关系、地形效果、资源再生速度。抽到的是哪一组不告诉 bot，只能从局内事件推断。
- **为什么不违反"难度不能来自隐藏要求"（DESIGN 1.2）：** 规则族全文和抽样分布都公开，隐藏的只是这一局抽到了什么。
- **考什么：** 探索和利用的权衡、在线推断、泛化。
- **可参照的已有设计：** ARC-AGI-3（没有说明的交互游戏）；据参赛者的赛后总结，Lux AI 第三季也有局内不可直接观测的常数（官方规则未细查）。
- **阶梯：** 推断加规划的 bot，按推断所用的样本量或先验强弱分级。另做一个"知道真实参数"的 bot 作上界参考，不进阶梯。
- **风险：** 和对手建模轴不容易分开，方差大。

**建议的顺序：**

1. **先做 G4。** 阶梯最便宜，补的正好是前哨的空白。
2. **第二款在 G2 和 G3 之间选。**
3. **G1、G5、G6 放到后面。** 这三款贵，风险也高。

每款都先在公开图上做原型筛选，照前哨深度原型的办法：先预登记，一半地图调参、一半出结论，配对差的区间不能含零。过筛之后，才走完整的 A/B/C。

## 6. 两种模式："写 bot"和"实时对局"

| | 写 bot（HRW 现在的做法） | 实时对局（模型每回合直接出招） |
| --- | --- | --- |
| token 成本 | 每款游戏每个模型有固定上限。HRW 1.0.0 是两阶段合计不超过 6M + 8M | 约等于 局数 × 每局决策次数 × 每次决策的 token |
| 评分局数 | 不花 token。一次评分 392 局，开发机上中位 40.3 秒（`reports/phase-C.md`） | 每多一局都要花 token |
| 计时公平 | 按 CPU 时间计，加机器锁（第 2 节） | 只能按墙钟或 token 计，受服务端负载影响 |
| 考什么 | 设计、实现、调试、利用反馈 | 当场推理、局内适应、自然语言谈判 |
| 主要风险 | 编程能力和策略能力混在一起 | 成本高，提示和解析器的设计影响结果（Kaggle Game Arena 报告对此有讨论） |

**举例：** 前哨一局 300 回合，评分 392 局，实时模式要做 117,600 次决策。每次决策按 3,000 token 算（局面就有几十行），约 3.5 亿 token，比写 bot 的上限高一个数量级以上。就算换成 50 次决策、100 局的短游戏，也要约 1,500 万 token。具体能不能承受，要对照 AgentEvalLab 的单模型 token 总目标（见 AgentEvalLab 设计文档）。

**建议：**

- 正式分数一律用写 bot 模式；
- 实时模式只用于三件事：G5 的自然语言谈判研究；用于宣传的展示对局（参照 AI Diplomacy 的直播）；少量对照局，看两种模式的排名是否一致；
- 可以考虑一种折中的"教练模式"：模型在多轮之间修改自己的 bot，类似 CodeClash 的多轮锦标赛。这就是把 HRW 的练习赛交接推广到 k 轮，token 仍然有上限。

## 7. 怎样检验这些游戏真的区分了能力

要回答的问题是：几款游戏给出的模型排名，是不是只是同一个"总能力"的重复测量。

**步骤：**

1. **数据。** 每个模型在每款游戏上至少有一份最终提交的阶梯分和区间。一部分模型同一游戏开两次独立会话，用来估计会话间方差，也就是重测信度。HRW 目前每种条件只有一次会话，这是最大的缺口。
2. **先算每款游戏自身的信度。** 包括同模型两次会话的一致性，以及地图簇 bootstrap 的方差（`arena/scoring.py` 已有）。
3. **游戏间相关去衰减。** r_ij ÷ √(rel_i × rel_j)。去衰减之后仍明显小于 1，才能说两款游戏测的不是同一件事。
4. **描述性主成分。** 看第一主成分解释了多少方差，按模型家族做留一，检查结果是否稳定。
5. **事先登记每款游戏针对的轴，再看排名在哪些游戏对上翻转。** Kaggle Game Arena 在国际象棋、扑克、狼人杀上就看到了"在单个游戏内强弱分层明显，但跨游戏不一致"。
6. **按能力和总体分别报告。** 这是用户 2026-11-26 的原则。

**至少多少个模型：**

- 正式的因子分析没有固定的最低样本量，取决于公因子方差和每个因子有几个指标（MacCallum 等 1999）；常见的建议是上百个样本。Observational Scaling Laws 用了约 100 个公开模型，lmgame-Bench 用了 13 个。
- 我们最多一二十个模型，所以只做描述性主成分和去衰减相关，不声称得到了因子结构。
- 经验估计（不是文献结论）：
  - 不少于 10 个模型，且来自至少 4 个厂商或家族，才值得看相关矩阵；
  - 不少于 20 个，才能对 5 款游戏做较稳的主成分，并用留一家族法检查。
- 同一厂商相邻的几个版本不算独立样本。

**改题的条件：** 某款游戏只有在伤到它所考的那种能力时才改，也就是区分不开，或者被一招鲜刷穿。改题的手段除了数值，也可以改形式或改判分标准（用户 2026-11-26 原则）。

## 8. 余量规则（从 HRW 带过来）

- **难度来自"种类"，不来自加量。** 模型在某款游戏上普遍超过约 0.9 时，发这款游戏的新规则版本，加深游戏本身，不靠在阶梯顶上加级。HRW 1.0.0 的 L12 是一次有披露的例外：它是为结案加的，文档写明"下一版靠加深游戏拉开区分，不靠加级"（DESIGN 11.5 第 6 条）。
- **锚点是绝对的，版本冻结，从不重标。** 旧版本保留，旧提交可以在新版本上重新评分（DESIGN 15.1–15.2）。
- **立项前先做天花板实验。** 让加力作者在更大的预算下写 bot，量"多花工夫能多赢多少"。前哨的结果是对留出参照 65.08%，按 CA 的读法只算"部分"，它说明上限来自游戏本身。
- **原型阶段就要看时限有没有被用上。** 搜索轴尤其如此；前哨的教训是 61 ms 只用了 4.3 ms。
- **不能只看公开图。** 前哨第二轮作者在 public 图上的自测比 dev 图高约 14 个百分点（`inbox/2026-11-25-ceiling-result-review.md`）。新游戏同样要有隐藏的 dev、grading 和 holdout 图集。
- **单个机制往往不够。** CA 引 Halite、Lux、Battlecode 的经验：强度能拉开，靠的是多个机制相互作用。所以新游戏不要只围绕一个旋钮设计。

### 9.2 复现一局只要种子，还是要完整动作日志

**要完整动作日志。** 理由：

- 回放校验（`arena/games/outpost/replay.py` 的 `verify`）只重新执行引擎，从不运行 bot。它把记录下来的每回合原始回复行重新解析，核对被接受的指令、作废的指令和每回合状态哈希。
- 只有种子不够。bot 可以按剩余时间决定想多深，重打同一局结果可能不同（DESIGN 8.2）；隐藏 bot 的源码也不能公开重跑。
- 地图全文已经写在文件头里。只要引擎版本在 `arena/__init__.py` 的 `REPLAY_ENGINE_VERSIONS` 之内，回放就是自足的。

DESIGN 8.1 估计每局压缩后 30–60 KB。按这个估计，一次评分 392 局约 10–25 MB（估算，没有实测）。

### 9.3 要保留哪些数据

- **全部正式评分局的回放**（已经在保留），继续只存本机。
- **开发轨迹。** 完整的会话记录（工具调用、命令、输出）、每次本地 `check` 和 `tournament` 时 `bot/` 的快照摘要、模型自己跑的对局结果、`NOTES.md` 的各个版本。
- **练习赛记录。** 被测模型收到的反馈，原样保留。
- **token 和时间曲线。** 每个快照对应的累计 token（输入、输出、缓存分开）、墙钟和活动时间。
- **运行元数据。** 模型版本字符串、代理框架版本、计时锁摘要、评测机指纹。

这些都只能在宿主或 AgentEvalLab 一侧被动记录，不得改动发给模型的材料（见 paper-plans.md 第 5 节）。

### 9.4 可公开的展示池

隐藏内容永远不公开，所以展示要用一个单独的池子：

| 来源 | 能否进展示池 | 条件 |
| --- | --- | --- |
| 公开 bot（Z 动物园、M-balanced）之间在公开图上的对局 | 可以 | 要用户为展示池放开 2026-11-08 的"不上传回放"规定 |
| 模型提交对公开 bot、在公开图上的对局（例如练习赛） | 可以 | 同上，并且要用户同意公开模型提交（第 10 项） |
| 整版退役的阶梯 | 可以，在退役后 | 退役条件：这一版不再用于任何正式评分，下一版已经发布。退役后成员源码、地图和评分回放可以整体解密。DESIGN 16 已经有"泄露即作废、降为公开"的做法，可以作先例。解密之后旧分数仍然能复现，但这一版不再能抗污染 |
| 现役隐藏阶梯成员的任何对局或地图 | 不可以 | — |
| 模型提交之间的联赛（DESIGN 12.6，只报告不计分） | 可以 | 只用公开图 |

**存放：** Git 不放回放。`.githooks` 会拒绝，单文件也有 2 MB 上限。展示数据要放在 Git 之外，比如发布附件或单独的站点，具体怎么放由用户定。

**公开模型提交的副作用：** 公开之后，这些代码会进入后续模型的训练数据，可能抬高未来模型对公开 bot 的成绩。隐藏阶梯不受影响。

### 9.5 可视化

- **网页回放器。** 有两条路：
  - (a) 用 JavaScript 重写结算，再用状态哈希核对（DESIGN 8.2、15.4）；
  - (b) 用 Python 把每回合状态导出成 JSON 帧，网页只负责画。`verify` 已经有 `on_state` 回调，练习赛的 `turns.csv` 就是这样取数据的。

  建议先走 (b)。不用维护第二个引擎，保真由原引擎保证。
- **图表：**
  - 每个模型的能力画像（每条轴一格，附区间）；
  - 逐级得分曲线（`grade` 输出里已有 `levels`）；
  - 第一阶段到第二阶段的变化；
  - 强度随 token 变化的曲线；
  - 每回合 CPU 用量和时限的对比。

### 9.6 视频

素材只取自展示池。回放是确定性的，可以写代码逐帧渲染（HTML/Canvas），画面和解说按同一张时间表对齐。候选形式：

- 30–60 秒的决胜片段集锦，比如一次围攻或一次翻盘；
- "一个模型爬阶梯"：用逐级得分做柱状动画，画面只放它对公开锚点的对局，不放隐藏对手；
- 模型提交之间的联赛，做成赛事节目；
- 参照 AI Diplomacy，对展示联赛做直播，只用公开 bot 和模型提交。

## 10. 风险和未决问题

1. **阶梯成本。** 即使用搜索分级，每款游戏仍要校准、验收、做天花板实验。用 CA 的话说，一个新版本"代价接近把 A、B 阶段重做一遍"，以周计。
2. **顶端强度。** 搜索阶梯的顶端可能低于强模型能写出的水平。到时只能靠加大搜索预算，同时保证结构上的余量，比如更好的评估函数，或者限制工作量。
3. **风格单一。** 搜索阶梯的成员弱点相近，"一招鲜"检查可能更容易失败。
4. **非传递性。** 前哨的顶端已经是"谁克谁"多于"谁更强"（CA 2026-11-25）。G3、G5 会更明显。
5. **作者偏差。** 手写阶梯 bot 的模型家族可能占便宜，也可能吃亏（DESIGN 11.2）。
6. **编程能力和策略能力混在一起。** 写 bot 模式下，两者很难分开。可以试一个"给定强 SDK 骨架"的对照条件，但会改变任务，要另立版本。
7. **规则发现游戏（G6）和"难度不能来自隐藏要求"原则的边界**，要由 CA 裁定。
8. **多人游戏（G5）的锚定和评分方法**，HRW 没有先例。
9. **区分度检验需要的模型数，可能超过实际能评的数目**（第 7 节）。
10. **token 和 CPU 总预算。** 5 款游戏 × N 个模型 × 两阶段，要和 AgentEvalLab 的总预算对齐。评分本身的 CPU 不贵，开发会话的 token 才是大头。
11. **公开仓库。** 规划推上去就公开，见 paper-plans.md 第 6 节。
12. **题族分数怎么合**，需要统一，见 README"待用户定的事"第 10 项。
